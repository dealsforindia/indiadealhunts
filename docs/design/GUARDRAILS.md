# Guardrails

Apply to IndiaDealHunts work. Latest explicit user instruction wins. These rules do not add approval gates for authorized reversible work.

1. Scope each task to requirement IDs in REQUIREMENTS.md. This conversation supplies design intent. External sources supply implementation/library/animation mechanics; new visual direction requires user intent, not agent preference.
2. Preserve the functional skeleton, real data, affiliate destinations and unrelated uncommitted edits. No added delivery/location, chat assistant, invented ratings, live counts, unread badges or savings claims.
3. Accepted screenshots establish appearance only. Never infer animation, audio, libraries or measured performance from them. Label observed, inferred and proposed separately.
4. No generic minimalism, screenshot cloning or uniform green recolouring. Apply the agreed material hierarchy and information hierarchy. Generated mockups are proposals, not implementation authority.
5. Inspect winning selectors, token ownership and main.tsx import order before styling. Consolidate the affected rules; do not keep appending contradictory global overrides.
6. Finish the affected interaction states in both themes and mobile/desktop. Retain keyboard focus, touch alternatives, reduced motion and readable opaque fallback surfaces. Never apply parent opacity to make text translucent.
7. Prefer installed libraries. Before adding a dependency, document the requirement, existing alternative, licence, browser support and loading/runtime cost. Do not add one solely for fashion.
8. A prop must follow the visible character hand. Maintain sprite canvas, baseline, scale and identity. Key poses are not continuous animation. A placeholder is unfinished, not an accepted substitute.
9. Verify actual browser output. Build success is not visual evidence; screenshots are not motion evidence. Never claim refraction when only blur/gradients are implemented, or smooth FPS without measurement.
10. After two failed attempts at the same cause, inspect evidence and change approach. Ask the user only for an inaccessible asset, account action, aesthetic decision or real-device check that cannot be obtained independently. Do not repeatedly ask for existing authorization.
11. No deployment, bulk reset or unrelated deletion implied by a design task. Preserve working state and keep changes reviewable.
12. Close a task only against its acceptance criteria. Record remaining defects, actual checks and next step in STATE.md. Keep durable decisions separate from a growing work log.

User correction: refine the existing UI and flows. Do not introduce new sections, dashboards, workspaces or features as part of visual refinement. The added DiscoveryWorkspace was explicitly rejected and removed.
